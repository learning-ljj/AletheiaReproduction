# Round 1 口试准备稿

## 1. 问题域与目标

### 1.1 核心问题

本系统要解决的核心问题，不是简单地“让大语言模型更会做数学题”，而是**缓解大模型在复杂数学推理中的结构性不可靠问题**。这种不可靠主要体现在三类情况：

1. 推理链条容易出现局部逻辑跳步，结论看起来像对的，但中间缺少严格证明。
2. 模型容易把“语言上通顺”误当成“数学上成立”，出现幻觉式论证。
3. 模型通常缺乏稳定的自我校验与自我修正机制，无法主动识别和修复前一轮推理中的缺陷。

所以，更准确地说，本系统研究的是：**如何构建一个可迭代、可校验、可追踪的大模型数学推理框架，使模型输出不仅“像答案”，而且“经得起验证”。**

### 1.2 应用场景

这个系统面向的不是单一用户群，而是三类使用场景：

1. **研究者 / 开发者**：用于研究大模型在数学推理中的行为，分析其错误模式、修正能力和工具使用能力。
2. **评测场景**：用于在 IMOBench 这类数学基准上做批量测试，衡量系统是否真的比纯提示词方案更稳定。
3. **辅助解题场景**：在复杂题目上作为“推理助手”使用，但它的定位更偏向研究型辅助，而不是面向普通学生的即时解题器。

因此，系统的评价标准不能只看“最后答案对不对”，还要看：
- 推理过程是否可解释；
- 是否能识别并修复错误；
- 是否能沉淀可复用的中间知识；
- 是否能在基准数据上稳定运行。

## 2. 系统总体设计思路

### 2.1 设计哲学

系统的核心设计思想是“生成 - 验证 - 修订”的闭环，但它不是一个简单的循环，而是一个**分层的推理控制系统**。我把它拆成五层：入口层、编排层、执行层、记忆层、工具与评测层。

这种分层不是为了“把代码拆得更碎”，而是为了让不同职责彼此隔离：

- 入口层负责接收问题和配置，只处理输入与启动。
- 编排层负责决定下一步走向，只处理流程控制。
- 执行层负责真正调用模型，只处理单个阶段的推理。
- 记忆层负责保存状态、引理、历史和工件，只处理持久化。
- 工具与评测层负责给模型提供外部能力，并验证系统效果。

从架构风格上看，它更接近**分层架构 + 中央编排控制器 + 工具插件式扩展**的组合。核心不是把所有逻辑堆在一个大模型 prompt 里，而是把“推理”与“控制”分离开，让系统行为可以被观察和调试。

### 2.2 为什么要分成五层

这样分层的优势主要有四点：

1. **职责清晰**：每层只做一类事情，避免入口、推理、存储、工具混在一起。
2. **可审计**：每次阶段执行、每次工具调用、每次状态变化都能落盘，便于追踪。
3. **可替换**：如果以后要换模型、换工具、换评测数据，只需要替换对应层，不必动整个系统。
4. **可扩展**：当后续要加入新的检索方式、更多工具或新的验证策略时，可以在现有层之上扩展，而不是推倒重来。

### 2.3 顶层逻辑还是自底向上拼接

这个系统是**先有顶层逻辑，再逐层拆解实现**，不是自底向上零散拼起来的。也就是说，首先确定的是：

- 需要一个闭环推理流程；
- 需要一个验证驱动的路由机制；
- 需要把中间知识保存下来；
- 需要工具辅助模型做外部验证。

在这个前提下，才去拆分入口、编排、执行、记忆和工具模块。这样做的好处是模块边界和整体目标一致，不会出现“每个模块都能跑，但系统目标不清楚”的问题。

## 3. 关键技术方案选择与论证

### 3.1 编排层为什么采用“验证 -> 修订/生成”的线性闭环

编排层采用的是一个非常明确的有限状态机式流程：先生成候选答案，再验证，再根据验证结果进入修订或重新生成。这个方案不是唯一解，但它是当前最适合本系统目标的解。

#### 为什么没有采用并行多答案投票

并行生成多个答案再投票，优点是简单直接，适合封闭式题目；但它的问题也很明显：

1. **成本高**：要同时生成多个完整答案，token 消耗更大。
2. **解释弱**：投票只能告诉你哪个答案被多数接受，但不能说明为什么前一个答案错。
3. **难以沉淀知识**：它不擅长把错误转化成可复用的引理或修正经验。

而本系统更关注的是“推理过程中的纠错能力”，不是单纯的多数决。

#### 为什么没有采用树状搜索

树状搜索更像 AlphaZero 一类的策略：在多条推理分支中探索最优路径。它当然更强，但代价也更高：

1. 需要复杂的搜索策略和评估函数。
2. 需要更强的状态管理，否则树会迅速膨胀。
3. 对当前这个毕业设计来说，系统复杂度会明显上升，重点容易偏离“可解释、可验证、可复现”的目标。

#### 为什么最终选择有限状态机模型

因为这个模型有三个非常实际的优势：

1. **确定性强**：每轮的行为规则清晰，适合调试和答辩解释。
2. **控制成本**：每次只走一个明确的阶段，便于控制调用次数。
3. **适合闭环验证**：验证器的结论可以直接映射到下一步动作，形成稳定反馈回路。

所以，当前方案并不是“最强搜索”，而是**最符合工程可控性和科研可解释性的方案**。

### 3.2 验证器为什么要分成“分析 - 找证据 - 下结论”三段

验证器的三段式设计是整个系统里最关键的一个技术点。它的本质是把“思考”拆开，而不是让模型一次性完成所有工作。

#### 分三段的好处

1. **先理解问题，再寻找证据**：第一段先让模型形成整体判断，避免一上来就乱查。
2. **证据检查和主观判断分离**：第二段通过工具去核实事实，这一层尽量靠外部证据而不是纯语言直觉。
3. **最终裁决更稳定**：第三段汇总前两段的信息后再输出结论，减少随意跳变。

#### 如果把三件事混在一个 Prompt 里会怎样

如果把思考、找证据、下结论混成一个 prompt，常见问题有：

1. 模型容易在没有查证的情况下提前下结论。
2. 证据和判断混写，导致输出结构不稳定。
3. 一旦中间某一步错了，错误会被连带放大，难以定位是推理错还是证据错。

三段式设计的价值就在于：**把“想法、证据、判断”拆开后，每一层都更容易检查。** 这也是为什么本系统的验证器比普通“让模型自己审自己”的方式更稳。

### 3.3 记忆层中的引理是如何检索和利用的

当前系统里的引理记忆不是复杂的向量检索，也不是语义搜索排名，而是**轻量级的结构化回灌**。更准确地说，它使用的是：

1. 从 ProblemMemory 中读取已经保存的引理文本。
2. 通过 ContextBuilder 把最近的引理摘要和最近的错误提示提取出来。
3. 将这些内容按列表形式拼接进下一轮 prompt 中。

也就是说，当前记忆更像是“可控的上下文注入”，不是“智能检索引擎”。

#### 这说明记忆是负担还是资产

在这里，记忆是**资产**，不是负担。原因有三点：

1. 它把上一轮得到的有效结论保留下来，避免重复推导。
2. 它把已经验证过的引理作为后续推理的中间知识，提升连续性。
3. 它把错误提示也保存下来，供下一轮调整推理路径。

如果没有这层记忆，系统每一轮都像重新开始，会明显削弱闭环修正能力。

不过也要说明一点：当前实现仍然是“简洁优先”，不是大规模检索系统。它的设计重点是**先证明记忆能起作用**，而不是先追求最复杂的检索机制。

### 3.4 工具层为什么必要

工具层的必要性非常强，原因在于：纯大模型在复杂数学推理里往往擅长“生成看起来合理的文本”，但不擅长“自我验证”。

系统提供的工具，核心上是在补三种能力：

1. **Python 执行器**：用于做数值验证、小规模枚举和公式检查。
2. **artifact 读取器**：用于读取已经积累的引理、论文和其他中间材料。
3. **搜索与引用审查工具**：用于把外部证据纳入推理，而不是完全靠模型记忆。

#### 如果不提供工具会怎样

如果完全不提供工具，闭环系统并不是完全失效，但会退化成“多轮 prompt 改写”。这种情况下：

- 验证器只能依赖自身语言判断，证据性下降；
- 很多公式是否正确，无法做外部检查；
- 生成器和修订器很难主动利用已有工件；
- 系统整体更像一个“会反思的聊天模型”，而不是一个“有外部校验能力的推理系统”。

所以，工具不是锦上添花，而是闭环可成立的重要支撑。它让模型从“想答案”变成“想答案 + 查证据 + 修错误”。

## 4. 运行实例：一个能贯穿全文的典型案例

### 4.1 为什么选这个例子

我选择的案例是 `imo-bench-algebra-001`，题目是：

> 对于正整数 $N$，Henry 对每个 $1\le a,b\le N$ 的整数对，写下 $ab$ 除以 $N+1$ 的商，求所有满足总和等于 $\frac{N^3-N^2+2}{4}$ 的 $N$。

这个例子的优点是：

1. 它不是简单计算题，而是需要数论变形和结构性证明。
2. 它能体现“引理 + 主证明 + 终态验证”的闭环能力。
3. 它正好出现了“初稿思路对，但论证不够严谨”的情况，非常适合展示验证器的作用。

### 4.2 第一轮生成答案是什么样的

第一轮生成器实际上已经给出了一个完整的主线答案，最终结论也是 $N=3$。它的优点是方向正确，已经抓住了关键数论结构：

- 先把商和余数拆开；
- 再把问题转成余数总和；
- 然后引入与 $ab \bmod m$ 相关的引理；
- 最后把条件变成关于 $\sum_{d\mid m} \varphi(d)/d$ 的约束。

但这个初稿并不是完全严谨的。它的主要问题不在“结果错了”，而在“证明链条有缺口”。

### 4.3 验证器给出的反馈是什么

验证器在第一轮没有直接否定结论，而是判为 **MINOR_FLAW**。它指出了三个关键问题：

1. **引理中的计数论证不够严谨**：
   - 虽然引理的结论经过数值测试是对的，但“每个非零剩余类恰有 d 个解”的论证不完整。

2. **步骤 8 的乘积公式推导被省略**：
   - 即从 $\sum_{d\mid m}\frac{\varphi(d)}{d}$ 推到素因数分解形式的那一步，没有把积性理由说明白。

3. **输出契约不够规范**：
   - 验证器还认为初稿在格式契约上不够完整，说明系统对“结果正确”之外的结构要求也在检查。

这一步非常关键，因为它说明验证器不是只看答案对不对，而是会检查：
- 论证是否闭合；
- 关键跳步是否解释清楚；
- 输出是否符合约定格式。

### 4.4 修订后的答案做了什么补强

修订器接到反馈后，主要补强了两处：

1. **把引理证明改得更完整**：
   - 明确写出 $a=d a'$、$m=d m'$ 后的同余变形；
   - 说明在模 $m'$ 下为什么可以唯一求解；
   - 解释为什么每个非零剩余类对应恰好 $d$ 个解。

2. **把积性展开说清楚**：
   - 直接说明 $\varphi(d)/d$ 是积性函数；
   - 由素因数分解推出乘积形式；
   - 再用下界分析证明只能得到 $m=4$，进而推出 $N=3$。

这说明修订不是重写整题，而是**针对验证器指出的漏洞做定点修补**。这正是系统闭环的价值：不是推翻原答案，而是让原答案变得可证明。

### 4.5 最终输出是什么

最终输出的结论仍然是：**满足条件的正整数只有 $N=3$**。

这个结果的意义不只是“答对了”，而是证明了整个系统确实完成了以下闭环：

1. 生成一个候选解答；
2. 验证器发现其中的论证漏洞；
3. 修订器补上漏洞；
4. 验证器复核后判定正确；
5. 最终输出可用于展示和存档的答案。

### 4.6 这个案例为什么能体现系统优势

这个案例最能体现的优势是：

- 初稿并非完美，但系统没有因为局部漏洞直接失败；
- 验证器能识别“结论正确但证明不够严谨”；
- 修订器能利用反馈进行针对性补强；
- 最后结果不仅有答案，还有完整的证据链。

这正好说明本系统的价值不是“第一次就猜对”，而是**能把不完整的推理逐步修成完整推理**。

## 5. 可以直接用于答辩的总结表达

如果答辩老师让你用一句话概括这个项目，可以这样说：

> 本系统面向复杂数学推理中的幻觉、跳步和缺乏自我修正能力等问题，构建了一个以“生成 - 验证 - 修订”为核心的闭环推理框架，并通过分层架构、工具调用和持久化记忆，把大模型推理从一次性输出提升为可校验、可追踪、可复用的过程。

如果老师继续追问“为什么这个方案值得做”，可以继续补一句：

> 因为它不是只追求一个结果，而是同时追求结果正确、过程可解释、错误可修复、知识可积累。
