第三章 系统总体设计

本章从软件系统设计者的视角，说明本项目如何把“自然语言数学解答”做成一个可迭代、可验证、可追踪的工程系统。这里不做空泛描述，所有关键结论都给出代码原文摘抄与精确行号范围。

3.1 设计目标与原则

本系统的设计目标可以概括为四条：第一，必须支持闭环迭代，而不是一次性输出；第二，流程控制与内容生成分离，避免把全部决策混在一个提示词里；第三，全过程落盘，支持复盘和审计；第四，允许把中间引理与错误信息沉淀下来，形成可复用资产。

本系统的核心是生成-验证-修订闭环，转移依据来自验证结论。该逻辑在编排器和恢复策略中是显式编码的。

    def route_on_decision(decision: VerificationDecision) -> str:
        if decision == VerificationDecision.CORRECT:
            return "FINAL"
        if decision == VerificationDecision.MINOR_FLAW:
            return "REVISER"
        if decision == VerificationDecision.CRITICAL_FLAW:
            return "GENERATOR"

说明：这就是轻量有限状态机。它不靠隐式提示词猜测下一步，而是用固定规则做可解释转移。

5.3 系统运行价值分析

从该案例看，系统价值主要体现在三点。

第一，验证器能把“结果是否正确”和“论证是否完整”区分开。首轮不是直接判错，而是 MINOR_FLAW，这使修订阶段有明确目标。

第二，修订阶段是定向修补，不是盲目重生成。历史事件可见 REVISER 紧接在首轮 VERIFIER 之后，且 turn_id 保持一致语义，保证反馈链条闭合。

第三，终态产物可审计。history.jsonl 记录全过程，state.json 记录结构化状态，manifest.json 给出最终摘要，final_output.md 保留验证输出与最终解答。

第六章 结论与展望

6.1 工作总结

本项目完成了一个计算机软件类毕业设计应具备的核心内容：
1. 实现了可运行的数学推理 Agent 系统，而非单个脚本。
2. 构建了生成-验证-修订的闭环编排机制，且转移规则可读可查。
3. 建立了问题级记忆与工件体系，支持状态快照、历史事件、引理沉淀和终态清单。
4. 在真实案例中验证了“初稿有缺陷 -> 验证定位 -> 修订补全 -> 成功收口”的流程有效性。

这些结论都在源码和运行文件中有明确证据支撑，不依赖主观推断。

6.2 未来工作展望

结合当前实现，后续可沿三个具体方向推进。

第一，将生成器拓展为更完整的搜索 Agent。当前生成器以单路径为主，未来可引入 Planner，决定何时拆分子问题、何时回溯、何时切换证明思路。

第二，扩展工具能力并把部分工具升级为子 Agent。当前 call_searcher 已在工具注册表中存在（src/tools/registry.py 第81-130行，第159-164行），后续可把检索、摘要、证据整理做成独立流程，降低主链上下文负担。

第三，把编排器从固定规则升级为“规则+智能”混合模式。现阶段 route_on_decision 是清晰可控的硬规则（src/core/recovery_policy.py 第28-38行）；未来可在保留安全边界的前提下，引入 Planner/Manager 对复杂问题做更灵活的路径规划。

总之，本项目已完成“从一次性生成到可校验闭环”的软件化落地。后续重点不是堆叠调用次数，而是在可控性不下降的前提下提升探索能力、证据利用能力和编排智能。
