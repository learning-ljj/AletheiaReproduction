# AletheiaReproduction 项目讲解文档

## 一、项目整体是怎么工作的

这个项目本质上不是“让大模型一次性写完答案”，而是把数学推理拆成一个可反复迭代的闭环：先生成候选解答，再验证，再根据验证结果修订，直到答案被判定正确，或者达到最大轮次后给出“尽力而为”的结果。这样的设计更接近真实科研推理过程，因为推理不是线性的，而是不断发现漏洞、补证据、再收敛的过程。

从工程实现上看，项目分成五层：入口层负责接收题目和配置；编排层负责决定每一轮该走哪一步；执行层负责让模型真正产出内容；记忆层负责把每轮过程、工件和状态保存下来；工具与评测层则负责给模型提供外部证据、以及对整套系统做批量验证。这样拆开以后，系统的每一层都很清楚自己该做什么，既方便讲解，也方便调试和复盘。

## 二、入口层：程序怎么启动

入口文件是 [main.py](main.py#L92)。这里最重要的事情只有四件：解析参数、加载配置、创建 Agent、把题目交给主流程。

代码上，入口先统一 Windows 下的编码输出，再决定题目来源是文件还是命令行直接输入，随后加载配置与提示词，最后创建运行对象并执行求解。关键逻辑可以直接从这里看出来：

```py
if args.problem:
    problem_text = args.problem
    problem_id = "inline"
elif args.problem_file:
    path = Path(args.problem_file)
    if not path.exists():
        print(f"Error: file not found: {path}", file=sys.stderr)
        return 1
    problem_text = path.read_text(encoding="utf-8").strip()
    problem_id = path.stem
else:
    parser.print_help()
    return 1

config = load_config()
prompts = load_prompts()
agent = AletheiaAgent(config, prompts)
state = agent.solve(run_id, problem_text, ground_truth=ground_truth)
```

这段代码对应 [main.py](main.py#L92) 到 [main.py](main.py#L206) 的主入口流程。它有一个很实用的设计：既支持“文件输入”，也支持“直接粘贴题目”，所以既适合正式评测，也适合调试单题。题目跑完以后，程序还会尝试重新读取 `state.json`，把运行期间积累的错误整理成更容易读懂的摘要，并在需要时生成工作日志 Markdown，这让结果不只是“有无成功”，而是“为什么成功或失败”。

与入口直接相关的配置加载在 [src/core/config.py](src/core/config.py#L24) 和 [src/core/config.py](src/core/config.py#L51)。这里的实现不是简单读一个 YAML，而是会递归替换环境变量占位符，并把 `config/prompts` 目录下的多个 YAML 合并起来。也就是说，项目把“参数”“提示词”“模型提供方”分开管理，便于替换环境、切换模型和调整 prompt，而不用改主代码。

## 三、编排层：谁决定下一步怎么走

编排层是整套系统的核心，入口在 [src/core/agent.py](src/core/agent.py#L117) 和 [src/core/orchestrator.py](src/core/orchestrator.py#L297)。如果只用一句话概括：它负责把“模型能力、工具能力、持久化能力”拼成一个稳定的推理流水线。

### 3.1 运行对象怎么装配

在 [src/core/agent.py](src/core/agent.py#L62) 里，系统先把模型客户端、工具 schema、工具执行器、阶段级 Agent 组装起来。这里有一个很关键的思想：不同阶段看到的工具并不一样。生成阶段只开放最少的读取能力，验证阶段才开放更强的检查能力。这样做的目的不是限制模型，而是让模型在不同阶段拥有合适的权限边界，避免“工具乱用”导致流程失控。

这段代码的作用可以理解成“装配车间”：它不是在推理，而是在搭积木。先把工具白名单筛出来，再把执行器套上一层权限控制，最后交给后面的编排器使用。

### 3.2 主循环怎么迭代

真正的迭代逻辑在 [src/core/orchestrator.py](src/core/orchestrator.py#L349)。它的工作方式很像“审题 - 作答 - 复核 - 再修正”：每一轮先让验证器判断当前解答有没有问题，然后根据结果决定进入修订还是重新生成，只有当验证器确认正确时才直接收敛到最终输出。

```py
for turn in range(1, self.max_turns + 1):
    state.iteration_count = turn
    decision, verification, verification_text = self._execute_verifier_node(state, turn_id=turn)
    next_node = self.recovery_policy.route_on_decision(decision)
    if next_node == "FINAL" and decision == VerificationDecision.CORRECT:
        result = self.finalizer_engine.finalize_success(...)
        return _finish(result)
    if next_node == "REVISER" and turn < self.max_turns:
        self._execute_solution_node(node="REVISER", turn_id=turn, verification=verification)
        continue
    if next_node == "GENERATOR" and turn < self.max_turns:
        self._execute_solution_node(node="GENERATOR", turn_id=turn, verification=verification)
        continue
```

这段主循环对应的不是单次问答，而是“有反馈的搜索过程”。验证结果并不只是一个标签，它会直接影响下一轮用哪种方式继续推理。换句话说，系统不是在盲目堆 token，而是在用验证结果驱动下一步动作。

### 3.3 验证结果怎么路由

路由规则在 [src/core/recovery_policy.py](src/core/recovery_policy.py#L28)。这里把验证结论压缩成三类动作：完全正确就结束，局部缺陷就修补，结构性问题就重做。这个映射很朴素，但非常有效，因为它把“模型判断”转换成了“流程控制”。

再往上一层看，恢复策略还提供了一个解析失败时的修复提示模板，位置在 [src/core/recovery_policy.py](src/core/recovery_policy.py#L42)。它的思路不是要求模型推倒重来，而是优先修格式、修结构，这样能把“内容正确但格式坏掉”的情况从真正的推理失败里区分出来。

### 3.4 终态怎么收口

收尾逻辑在 [src/core/finalizer.py](src/core/finalizer.py#L261) 和 [src/core/finalizer.py](src/core/finalizer.py#L291)。成功时，系统把最终解答、引用和警告整理成可展示文本；轮次耗尽但仍有进展时，会标记为 PROGRESS；如果没有实质推进，则标记为 FAILED。

终态处理并不只是“打印结果”，它还负责三件更工程化的事情：把最终解答保存为 Markdown、把运行摘要写入清单文件、把引用转换成 BibTeX。换句话说，最终输出既面向人看，也面向后续复用。

## 四、阶段执行：三个角色各做什么

### 4.1 公共执行骨架

所有阶段的共同运行逻辑集中在 [src/agents/base.py](src/agents/base.py#L52)。它的思路很简单：把系统提示和用户输入拼成一个对话，必要时走工具循环，不需要工具时直接让模型输出。阶段结束后立即清空临时消息，避免上一轮内容污染下一轮。

```py
if self.tools:
    response = self.llm_client.chat_with_tools(...)
else:
    response = self.llm_client.chat(...)

self.messages.append({"role": "assistant", "content": response.content or ""})
return LLMResponse(
    content=response.content or "",
    reasoning_content=getattr(response, "reasoning_content", "") or "",
    tool_calls_trace=getattr(response, "tool_calls_trace", []) or [],
)
```

这一层的重点不是“回答了什么”，而是“怎么把一次阶段调用包装成可审计的标准结果”。这样上层才能同时拿到正文、思维链痕迹和工具调用痕迹。

### 4.2 生成阶段

生成阶段对应 [src/agents/generator.py](src/agents/generator.py#L31)。它的输入结构很清楚：题目本身、历史引理上下文、上一轮验证反馈。也就是说，生成不是从零开始，而是带着已有知识和上轮失败经验继续往前走。

```py
parts = [problem_text.strip()]
if lemma_context_items:
    parts.append("\n\n---\nLemma Context:\n" + "\n".join(f"- {item}" for item in lemma_context_items))
if verification:
    parts.append("\n\n---\nVerification:\n" + verification.strip())
return "".join(parts)
```

这段逻辑的意义在于：生成器并不只是“写一份答案”，而是在已有上下文的约束下，生成尽量靠谱的候选方案。上下文越完整，后续验证就越容易聚焦在真正的数学问题上，而不是格式噪音上。

### 4.3 修订阶段

修订阶段对应 [src/agents/reviser.py](src/agents/reviser.py#L31)。它输入的是“题目 + 旧答案 + 验证报告 + 引理上下文”，比生成阶段多了一个很重要的东西：上一版答案本身。这样修订就不是重新写一篇，而是对现有答案做局部修补。

这个设计很符合实际推理：如果问题只是证明中某一步不严谨，最优策略不是整篇重写，而是沿着原结构补上缺口。这样既保留已有正确部分，也减少新错误引入的概率。

### 4.4 验证阶段

验证阶段对应 [src/agents/verifier.py](src/agents/verifier.py#L27)。它采用三段式结构：先做分析，再调工具，再给结论。工具调用主要在第二段完成，这样可以把“思考”和“证据检查”分开。

```py
phase1_resp = self.llm_client.chat(messages, thinking=True, stream_prefix="VERIFIER-P1")
phase2_resp = self.llm_client.chat_with_tools(messages, self.tools, self.tool_executor, ...)
self.llm_client.clear_reasoning_content(messages)
phase3_resp = self.llm_client.chat(messages, thinking=False, stream_prefix="VERIFIER-P3")
verifier_response = phase3_resp.content or ""
return verifier_response, tool_trace, preliminary_analysis
```

这一设计很关键。第一段负责“理解问题”，第二段负责“找证据”，第三段负责“给结论”。这样做的好处是，验证不再是模型自己拍脑袋下判断，而是有了证据链支撑。

## 五、记忆层：状态、工件和错误怎么留存

记忆层的目标不是存一堆日志，而是把整个推理过程变成“可以回放、可以定位、可以继续利用”的数据结构。核心实现是 [src/memory/problem_memory.py](src/memory/problem_memory.py#L34) 和 [src/memory/state.py](src/memory/state.py#L207)。

### 5.1 状态快照

运行时状态定义在 [src/memory/state.py](src/memory/state.py#L308)。`ProofState` 保存题目、当前答案、轮次、最终结果等运行期字段；而 `ProblemSnapshot`、`StageSnapshot`、`EventSnapshot` 则负责持久化，让后续分析可以按轮次回看。

更重要的是，系统还提供了错误汇总函数，位置在 [src/memory/state.py](src/memory/state.py#L324)。它会把 state 里每个阶段记录到的 error 汇总成用户可读的一段话。这很像“日志摘要”，但它不是原始堆栈，而是更适合展示和汇报的版本。

### 5.2 问题级持久化

问题记忆管理器位于 [src/memory/problem_memory.py](src/memory/problem_memory.py#L74)。它负责建目录、写状态、写历史、写工件。这里最核心的几个动作分别对应：

- [src/memory/problem_memory.py](src/memory/problem_memory.py#L97)：把当前状态写入 `state.json`。
- [src/memory/problem_memory.py](src/memory/problem_memory.py#L122)：把阶段事件写回 state，形成可回放的阶段轨迹。
- [src/memory/problem_memory.py](src/memory/problem_memory.py#L211)：把每次运行的事件追加到 `history.jsonl`。
- [src/memory/problem_memory.py](src/memory/problem_memory.py#L312)：把新引理写入 `artifact/lemmas`，并处理重复内容与文件名冲突。

这里的设计非常适合做科研型系统，因为它把“推理过程”变成了真实落盘的知识资产。比如引理不仅是中间结果，也能在下一轮被重新读出来、重新组合。

### 5.3 引理、论文和终态工件

除了引理，系统还支持论文工件和最终清单：论文写入 [src/memory/problem_memory.py](src/memory/problem_memory.py#L436)，BibTeX 写入 [src/memory/problem_memory.py](src/memory/problem_memory.py#L459)，运行清单写入 [src/memory/problem_memory.py](src/memory/problem_memory.py#L473)。这说明项目不是只关心“答案对不对”，还关心“证据来源是什么”“最终结果怎么归档”。

## 六、LLM 与工具层：模型怎么接外部能力

### 6.1 模型客户端

模型接口在 [src/models/llm_client.py](src/models/llm_client.py#L25)。它把 provider 的差异隐藏起来，对外提供统一的 `chat` 和 `chat_with_tools` 两种调用方式。前者适合纯生成，后者适合需要调工具的场景。

```py
def chat(...):
    reasoning_content, content, _ = self._stream_transport.stream_completion(...)
    return LLMResponse(content=content or "", reasoning_content=reasoning_content or "")

def chat_with_tools(...):
    content, last_reasoning, trace = self._tool_call_session.run(...)
    return LLMResponse(content=content or "", reasoning_content=last_reasoning, tool_calls_trace=trace)
```

这里最值得强调的是 `tool_calls_trace`。它的作用不是给模型看，而是给系统看：系统可以知道模型到底试了哪些工具、工具返回了什么、这些证据是否有助于最后的判断。这是可审计性的关键一环。

### 6.2 工具注册与执行

工具分发逻辑在 [src/tools/registry.py](src/tools/registry.py#L18)。它先检查工具名是否在白名单里，再把参数交给对应工具实现。换句话说，这里是一个统一入口，不同工具不需要单独暴露给上层。

比较有代表性的工具是：

- `run_python`：执行代码并返回 stdout、stderr 和退出码。
- `call_searcher`：调研搜索管线，返回论文、错误和恢复信息。
- `read_artifact`：读取已落盘的证据文档。
- `review_citation`：检查引用是否与问题内的证据一致。

其中搜索相关逻辑在 [src/tools/registry.py](src/tools/registry.py#L81) 附近，体现了一个重要理念：工具不仅要返回结果，还要返回“过程中的错误和恢复信息”。这让模型可以基于失败信息继续调整，而不是把失败当成黑洞。

### 6.3 安全读取工件

artifact 读取工具在 [src/tools/artifact_reader.py](src/tools/artifact_reader.py#L84)。它只允许读取 `runs/{problem_id}/artifact` 下的 Markdown 文件，并支持按层提取内容：前置 YAML、证明主体、来源信息。这种分层读取适合让模型“按需取证”，而不是一次把整个文件吞进去。

安全性来自路径校验，机制在 [src/tools/artifact_reader.py](src/tools/artifact_reader.py#L53)。这类限制很重要，因为工具一旦能读文件，就必须防止越权读取系统任意路径。

## 七、配置层：为什么能灵活切换环境和提示词

配置加载在 [src/core/config.py](src/core/config.py#L9) 到 [src/core/config.py](src/core/config.py#L51)。这一层做了两件事：

1. 读取 YAML 配置时递归替换环境变量占位符，这样密钥、地址等敏感信息可以从环境变量注入。
2. 从 `config/prompts` 目录加载多个 prompt 文件，并把同类配置合并起来。

这说明项目不是把 prompt 写死在代码里，而是把 prompt 当成可配置资产管理。这样做对研究类项目尤其重要，因为你可能会频繁调整验证模板、生成模板、修订模板，而不希望改核心逻辑。

## 八、评测层：怎么批量跑 benchmark

数据加载器在 [evaluation/data_loader.py](evaluation/data_loader.py#L105) 附近，提供了 `answerbench`、`proofbench`、`gradingbench` 三类数据读取和 ground truth 回填。它做的是“把 CSV 变成统一字典结构”，让上层不用关心原始表格字段名差异。

批量评测入口在 [evaluation/run_imobench.py](evaluation/run_imobench.py#L59) 和 [evaluation/run_imobench.py](evaluation/run_imobench.py#L277)。它会遍历数据集、逐题调用 `AletheiaAgent.solve`、统计 `SUCCESS / FAILURE / SKIP / ERROR`，并把结果写回 JSON 文件。这样就可以用统一脚本比较不同题集上的运行情况。

这个模块的定位很明确：它不参与推理，只负责验证系统在基准数据上的表现。对毕业设计来说，这一层非常重要，因为它能把“系统看起来能跑”变成“系统在一组标准题上真的能跑”。

## 九、运行产物长什么样

每道题运行以后，都会在 `runs/{problem_id}/` 下生成一套可追踪产物：

- `state.json`：当前题目的结构化状态。
- `history.jsonl`：按事件追加的运行日志。
- `artifact/lemmas/`：过程中沉淀出的引理。
- `artifact/papers/`：检索或整理出来的论文工件。
- `artifact/errors/`：错误记录。
- `artifact/citations.bib`：引用条目。
- `artifact/final_output.md`：最终输出。
- `artifact/manifest.json`：运行摘要和产物索引。

这套设计的价值在于，它把一次推理任务变成了一份可审计、可复用、可展示的研究记录。对于答辩来说，你不仅能展示结果，还能展示过程。

## 十、如果用答辩语言来概括这个项目

可以把这个项目概括成一句更学术也更通俗的话：它用“生成 - 验证 - 修订”的闭环，模拟人类数学推理中的反复校验过程；再通过持久化记忆、工具调用和基准评测，把原本难以解释的大模型推理变成了可追踪、可审计、可复用的工程系统。

如果导师追问“它为什么比一次性生成更可靠”，最核心的回答是：因为它不是只靠一次输出，而是把验证意见、外部证据、历史引理和错误摘要都纳入了下一轮决策。也就是说，系统会随着推理过程不断积累证据并修正路径，而不是把第一次答案当成最终答案。
